### 1. Реализованный функционал и архитектурные решения

* **Добавлена сущность Event**: реализована JPA-модель с полями `id`, `name`, `startTime`, `endTime` и связью Many-to-Many с Venue. Проведена миграция БД (Flyway).
* **GraphQL API (Netflix DGS)**:

    * Создание события (`createEvent`) через mutation с передачей `venueReferenceIds`, имени и дат.
    * Получение списка событий с информацией о площадках.
    * Расширен тип Venue: добавлена возможность получать последние N событий для площадки.
    * Получение списка площадок с их последними событиями.
* **Архитектура**:

    * Использованы DDD-слои: domain, dao, слой Sot для инкапсуляции доступа к данным.
    * Маппинг между слоями через MapStruct.
    * Логика сохранения реализована через публикацию событий в ApplicationEventPublisher.
* **Тестирование**:

    * Написаны unit-тесты (JUnit5 + Mockito) для основных сервисов и dao-слоя, включая проверку edge-case-ов и базовых нагрузочных сценариев.

### 2. Возникшие трудности

* **Согласование схемы БД и JPA-сущностей**: возникала ошибка несовпадения имён колонок между схемой и аннотациями JPA (`external_id` vs `externalId`), из-за чего Hibernate не находил нужные столбцы.
* **Работа с composite primary key** в Venue: требовалось корректно описать ключ через @IdClass и обеспечить правильное связывание с Event.
* **Сложности с типами дат** (String в GraphQL vs LocalDateTime в JPA): требовалась промежуточная конвертация через мапперы.
* **Тестирование интеграции Many-to-Many**: требовалось правильно подготавливать тестовые данные и мокать зависимости.

### 3. Решение проблем

* Явно указаны имена колонок через аннотацию `@Column(name=...)` для всех сущностей, чтобы избежать проблем маппинга.
* Для composite primary key использован отдельный Serializable-класс, что обеспечило поддержку сложных ключей.
* В MapStruct и мапперах реализованы методы преобразования между строковым представлением дат (GraphQL) и LocalDateTime (JPA).
* Для unit-тестов использовано активное мокирование всех зависимостей, реализованы тесты для проверки негативных сценариев и поведения на edge-case.

### 4. Что можно улучшить

* **Тестовое покрытие**: добавить интеграционные тесты с использованием TestContainers для проверки работы с реальной БД.
* **Обработка ошибок и валидация**: реализовать централизованный обработчик ошибок и валидацию входных данных на уровне GraphQL API.
* **Производительность и оптимизация запросов**: добавить DataLoader для устранения проблемы N+1, оптимизировать выборки через кастомные репозитории.
* **Документирование**: расширить документацию по API (например, использовать GraphQL Playground с примерами запросов).
* **Автоматизация CI/CD**: интегрировать пайплайн для сборки, проверки и публикации приложения.
* В предоставленном коде событие VenueSave публикуется через eventPublisher.publishEvent(it) ещё до того, как данные о площадке гарантированно сохранены в базе (сохранение происходит уже в слушателе через репозиторий) — это может привести к рассинхрону между доменной логикой и данными.
